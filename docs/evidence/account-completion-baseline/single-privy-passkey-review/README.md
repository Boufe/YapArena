# Independent Privy passkey boundary review

The Redis/financial reviewer independently read the provider passkey bridge, first-key policy, restart module, migrations 12000/13000 and retained operation consumption. [source-hashes.json](source-hashes.json) identifies the reviewed source, including uncommitted shared changes. This is a static review, separate from the module author's native browser/PostgreSQL execution.

No remaining authorization bypass was identified within this scope. The reviewed boundaries are:

- Provider identity, credential set and public key come from uncached server verification. A browser-supplied account ID or public key cannot authorize the bridge. Provider IO finishes before acquiring database connections and transaction locks.
- The intent binds the existing cookie hash, internal account, credential generation, provider subject, origin, RP, before digest and exact addition/existing-key mode. Candidate credential/public-key/session digests become immutable once captured. Concurrent retries recheck the same state.
- Completion acquires the provider DID advisory lock before the account/proof locks, then rechecks the active original session, mapping generation, baseline, candidate and expiry. A retained proof authorizes only `provider.passkey.link` with the exact stored terms and is consumed in the same transaction as activation.
- A native assertion must verify the exact trusted key, challenge, origin, RP and user-verification flag. Account key identity/provenance is immutable. Activation records the provider SID fence, consumes the intent, rotates application credentials through the existing key trigger and returns only the new application session cookie. Provider mapping generation remains fenced until the separate provider-reset outbox finishes.
- The before-funds exception checks historical accepted keys, linked-wallet and credential history, coin balances/postings, grants and nonquoted financial requests. Removing a prior key does not restore eligibility. Ordinary existing accounts require a retained credential.
- The restart is confined to an unfinished first key on an eligible account. It requires a fresh, unconsumed provider SID after the mapping's minimum time, no unresolved provider reset and a matching mapped generation, an exact sole passkey addition and the original intent's account/subject/baseline/origin. The approved uncaptured-candidate case still verifies the sole current key against the baseline. A new bounded one-use challenge requires user verification from that same key; atomic completion consumes the SID/challenge and rechecks expiry. It grants no money or general recovery override.
- Migration permissions expose only necessary runtime intent/candidate/consumption columns. Immutable history and one-completed-bootstrap-per-account constraints retain replay fences.

Review follow-ups were resolved before the final fixture run: asynchronous browser completion now receives an account/provider actor abort signal before entering the cookie-issuer queue; the actual clicked opener is passed through the approval helper instead of being rediscovered after React disables it. The maintained browser fixture asserts the queued stale completion never submits and cancellation restores the exact opener. Execution results are recorded separately and must be read with their own source/asset fingerprints.

This review does not establish genuine Privy public-key availability, hosted key enrollment, provider reset success, paid-plan eligibility, physical-device behavior or full WCAG acceptance. Intercepted SDK responses and virtual authenticators cannot substitute for those provider/hosted checks. It does not authorize live funding or redemption.
