## Build and type evidence

`tsconfig.frontend.json` checks browser source with strict DOM/DOM.Iterable types,
`noUncheckedIndexedAccess` and no ambient Node types. `tsconfig.service-worker.json` checks
`sw.ts` separately with WebWorker types and no DOM/Node globals. The isolated Node build tool
has its own strict project. Compiler file-list inspection found zero `@types/node` files in
the browser project; negative probes rejected implicit-any input and Node `process`, and
rejected `process`/`document` in the worker project.

`npm run typecheck:frontend` is in `npm run typecheck`, `npm run check`, `npm run build`
and the reusable CI quality workflow. Source-policy negative probes rejected handwritten
frontend JavaScript and tracked served source. Every `public/**/*.js` file is ignored build
output. `npm run dev` first generates assets and watches frontend/shared discovery sources;
the watcher rebuilt an edited module and stopped cleanly. The runtime still loads only
`.env.runtime`.

Two independent clean source-package builds, without `.git` or any preexisting public
JavaScript, passed using Node 24.19.0 and the existing locked dependencies (shared
`node_modules`, not a fresh installation). They generated exactly the existing 33 module
URLs and four bundle URLs. No missing or extra JavaScript assets were emitted. The independent final confirmation used
explicit Node 24.19.0 in `/private/tmp/yaparena-independent-node24-ej7ur6g4`; it replaces an
initial independent clean-build attempt that had resolved the host Node 25 from its external
working directory. All four
bundles have identical executable tokens after resolving minifier binding names; replay
and hero-live bundles are also byte-identical. Classic account scripts retain global scope;
ES modules retain their original mode. `arena.ts` has an explicit empty export because its
existing script tag is `type="module"`, avoiding Annex B aliases during emission.

## Existing checks and limits

Final quality gates, builds, disposable-database suites and both frozen-animation runs used
explicit Node 24.19.0. The initial baseline archive build and homepage/hero verifier launches
used the host Node 25.6.1 with the same locked dependencies and Chromium; their before/after
application screenshots match exactly. The initial in-app browser connection failed because its
runtime import of `node:process` was blocked; existing Chromium CLI verifiers were used instead.
The sandbox blocked loopback listeners and one filesystem watcher; checks passed when rerun
with the required execution permissions.

- `npm run build`, `npm run lint`, `npm run format:check`, `npm run typecheck` and
  `git diff --check`: pass.
- `DATABASE_TEST_MODE=host A4_QUALITY=true A4_BROWSER=true npm run verify:database-isolation`:
  pass against disposable PostgreSQL 17.10. Its full `npm run check` supplied A4, wallet and
  revocation test identities: **502 passed, zero failures/skips**, coverage **94.75% lines,
  93.11% branches, 95.79% functions**. Fresh/upgrade SQL isolation checks passed.
- The same harness initially passed existing A4/arena/shared-bot browser checks: commitment review and
  receipts, processing controls, sealed data, actual worker settlement, history/charts,
  hover/median/argument animation, reduced motion, expansion/Escape bounds restoration,
  sidebar/header, mobile overflow, accessibility, and uninterrupted synthetic replay passed.
- A repeat after the final arena module-mode annotation again passed all 502 quality tests,
  then failed the existing A4 browser assertion at `scripts/verify-a4-browser.js:224`
  (`receipt.executed === true`). The fixture leaves epsilon at 50,000 (5% exploratory
  pricing); `priceRound` may draw a uniform offer and `executeRound` requires accepting
  orders on both sides. Execution and positive payout are therefore not guaranteed for its
  NO ceiling of 0.78. A deterministic engine counterexample on both baseline and migrated code confirms that
  this assertion is not unconditional: 250 NO limits at 0.22, 250 YES at 0.34 and the human
  NO at 0.22, with an exploratory offer near 0.5, leave the human accepted but unexecuted
  with no accepting opposite side. Both revisions return the same result. The actual failed
  browser run’s sampled words/offer were not retained; exploratory pricing is a supported
  explanation, not an observed diagnosis of that draw. Source/runtime parity and the initial
  complete browser pass show no migration difference. No source, expectation, seed or
  threshold was changed to force execution. The failed repeat is retained in
  `/private/tmp/yaparena-ts-final-isolation.log`; its quality portion passed. The unchanged browser rerun passed A4, arena, shared-bot and fresh/upgrade SQL checks;
  `/private/tmp/yaparena-ts-final-browser.log` and the fresh
  `/private/tmp/yaparena-ts-evidence/a4-final/` artifacts record that outcome. The original
  probabilistic assertion remains unchanged and can still fail on future draws.
- `COMMUNITY_POSTGRES_MODE=host COMMUNITY_CLIENT_ONLY=1 node scripts/verify-community-local.js`:
  pass, including deterministic browser transport races, request identity, draft recovery,
  IME/focus, history/cursors/retention/reconnection, responsive/zoom and accessibility checks.
- Plain `npm run check` without disposable database URLs has a **pre-existing** line-coverage
  failure: baseline 89.49%, migrated 89.64%, threshold 90%. Both have 451 passing assertions,
  zero failed assertions and one skip. Thresholds and expected outputs were not changed.

No hosted deployment, real LiveKit session, real wallet extension, physical-device/acoustic/

## Suspected existing issues preserved

Typing exposed these assumptions; none was fixed or reproduced as a separate defect here:

- A4 selection temporarily stores only a run ID while refresh is pending; existing input
  estimation assumes `run.config` is already loaded.
- Wallet-change asynchronous callbacks assume pending operation state remains present even
  if the dialog is cancelled while a request is in flight.
- Existing Hls construction passes `autoLevelCapping`, which is absent from the installed
  `HlsConfig` declaration. The same option remains in the emitted code; its handling was
  not changed or inferred from the type declaration alone.
