## Staging trial procedure

1. Deploy the reviewed media fixes to the staging branch, confirm `/ready` is 200, and record the deployed commit SHA and UTC time. Open the staging HTTPS URL directly; public pages need no shared password. Account sign-in remains required for speaker and operator actions.
2. Prepare separate speaker A, speaker B, and operator test accounts. Publish profiles for both speakers. The operator account needs the `operator` role in `account_roles`; no operator profile or public role-grant endpoint is required. Staging user ID `3` has the role; sign in with that account and verify `/api/me/roles` reports `operator`.
3. At `/match`, use the existing test topic or publish a new one. Speaker A creates a direct challenge for side A; speaker B accepts side B. Record the event ID and URL. The UI requires scheduling at least one hour ahead, but an operator may start a ready event at any time once both speakers are connected. Record the planned and actual start times. Confirm the event uses `prototype-media-1`; older `preview-1` examples cannot start media.
4. On separate camera/mic devices and networks, each speaker opens the event page and selects **Check camera and join as speaker**. Verify the first speaker sees their own camera before the second joins, and that the speaker Join control disappears once connected. Check an unrelated signed-in account: it must not see a speaker Join control, and a direct speaker-token request must be denied. An anonymous viewer selects **Join as viewer**. Record device/browser/network, UTC join time, first local/remote video time, first audible speech time, and any permission or console error. Check that only the active speaker's microphone is audible.
5. The operator enters a reason and selects **Start**. Measure the time until speaker A's microphone is audible and observe at least two one-minute turn changes on all three screens. Reload speaker B's page: verify the operator sees a pause incident and the clock freezes, while B automatically attempts to reconnect without clicking; if browser permissions require a gesture, record that and use the fallback button. Once both speakers are connected, the operator selects **Resume**. Verify the correct side and remaining clock resume. Reload the viewer page separately and check playback recovery. Record clock differences and recovery times.
6. Switch one speaker's camera/microphone, then interrupt and restore that speaker's network. Record whether the operator sees a pause and incident, whether speech stops, whether the speaker reconnects automatically, and whether **Resume** restores the correct turn. Repeat on a mobile browser; inspect portrait video orientation and sharpness on the live page and replay, controls, focus, captions, and audio routing. These are human-observed checks.
7. The operator selects **End**. Verify both speakers' camera/microphone capture and live video tiles stop without refreshing. Record the time until recording status becomes `ready`, the LiveKit Egress ID/status, R2 object size, and any webhook or worker errors. Select **Publish replay**, play the full video as a fresh viewer, and check picture, both speakers' audio, sync, and ending. Publish reviewed WebVTT with the operator control and verify visible, synchronized captions on desktop and mobile.
8. Save the event ID, deployed SHA, UTC timestamps, device/browser versions, request IDs or redacted logs, R2 object size, and screenshots or short clips of failures. Never save tokens, passwords, signed replay URLs, or private media in Git. Enter measured results below.
